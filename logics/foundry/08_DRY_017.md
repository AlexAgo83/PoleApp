# 08_DRY_017 — Sécuriser inscription + archivage entités + droits profs
[Aligné v0.14.0 | Compréhension: 100% | Confiance: 95% | Avancement: 80% | Portée: signup vérif email + archivage studios/disciplines/utilisateurs + droits prof/preset]

## Objectif
Répondre aux retours QA S016 (v0.13.6) : durcir l’inscription (double saisie + affichage mot de passe + vérification email obligatoire), permettre l’archivage/désactivation non destructif des studios, disciplines et utilisateurs, et cadrer les droits profs (création position/preset + disciplines favorites). Décisions intégrées (durée lien, rate-limit renvoi, comportement cours existants, audit, droits profs) ; contenu FR pour démarrer (penser i18n plus tard si prévu).

## Périmètre (in/out)
- (in) Signup/login : formulaire création de compte, vérification email, blocage login si non vérifié, actions super-admin (forcer vérif, renvoyer email).
- (in) Archivage/désactivation : studios, disciplines, utilisateurs (élève/prof/admin) masqués sans suppression ; RBAC admin/super-admin.
- (in) Droits profs : permission “peut créer position/preset” (default on), disciplines favorites pour prof (équivalent positions coups de cœur).
- (out) Suppression physique des entités ; autres rôles/ressources non mentionnés ; flows multi-écoles avancés.

## Règles fonctionnelles détaillées
### Inscription / vérification email
- Champs obligatoires : prénom, nom, email, mot de passe (2 champs “mot de passe” + “confirmation”), acceptation CGU si déjà existante.
- UI : icône “oeil” sur chaque champ mot de passe pour afficher/masquer en clair.
- Création compte : enregistre l’utilisateur en état `unverified` ; affiche un message post-submit “Compte créé. Vérifie ton email pour l’activer.”.
- Email de vérification : envoyé automatiquement en arrière-plan (lien valable 24h) ; renvoi max 3 fois / 24h / utilisateur. Réutiliser le template FR existant (commentaire : prévoir i18n plus tard) avec fallback EN minimal si locale non FR. Lien vers `/auth/verify` (frontend) qui appelle l’API de validation et reprend la logique `/login` (redirige vers l’accueil du rôle).
- Login : refuser l’auth si l’utilisateur est `unverified` ; message “Compte non vérifié, consulte ton email ou renvoie un mail de vérification”.
- Reset password : bloquer dès la demande si utilisateur `unverified` ou désactivé (pas d’email de reset envoyé).
- Super-admin : peut marquer un compte comme vérifié (forcer vérif) et renvoyer un mail de vérif ; log d’audit si disponible.
- Redirection post-verify : par défaut vers l’accueil du rôle ; si un onboarding obligatoire existe, l’enchaîner après vérification.

### Archivage / désactivation (non destructif)
- Studio : action admin pour “désactiver” → le studio n’apparaît plus aux utilisateurs (listes/choix), mais reste en base (réactivable). Pas de sélection possible dans les formulaires si désactivé.
- Discipline : action admin pour “désactiver” → retirée des sélecteurs utilisateurs, non supprimée, réactivable.
- Cours existants liés à un studio/discipline désactivé : restent visibles/ouverts pour les inscrits avec badge “Désactivé” (élève/prof). Tooltip source (studio/discipline/prof) uniquement côté staff (liste cours, détail cours) et dans les sélecteurs studio/discipline. Réservation/paiement autorisés pour les inscrits actuels uniquement (pas de nouvelles inscriptions après désactivation). Création/édition de nouveaux cours avec une entité désactivée interdite. Sur lien public ou tentative non-inscrit : refus explicite “Inscriptions closes” (pas de redirection dédiée).
- Utilisateur : admin/super-admin peut désactiver un élève ou prof ; super-admin peut aussi désactiver un admin. Un utilisateur désactivé ne peut plus se connecter ni être assigné à de nouveaux éléments ; historique conservé. Si prof désactivé et seul sur un cours futur, le cours reste publié avec badge (pas de notif auto élève, gestion manuelle admin).
- Effet transverse : filtrer les entités désactivées des listes publiques/privées (cours, sélecteurs, etc.) ; préserver les données historiques (cours passés, positions).

### Professeurs : droits et préférences
- Droit “Créer/Supprimer position/preset” : deux flags globaux `canCreatePositionAndPreset` (duplication/import = créer) et `canDeletePositionAndPreset`. Si `create` retiré : bloquer création/duplication/import sur tous les flux (UI et imports). Si `delete` retiré : bloquer suppression. Un prof ne peut éditer que ses propres contenus (pas ceux des autres). Extension en 4 flags (position vs preset) reportée si besoin métier ultérieur.
- Disciplines favorites prof : sélection multiple (max 5) persistée ; usage en affichage profil, filtre/suggestion. UX alignée avec “positions coups de cœur”.

## Données / modèle (proposé)
- Utilisateur : états `verified` vs `unverified`; champ `forcedVerifiedBy` (optionnel) si super-admin force la vérif ; timestamp `verifiedAt`. Flag `disabledAt` + `disabledBy` pour désactivation (mieux que bool).
- Studios/Disciplines : `disabledAt` + `disabledBy`. Filtrer côté requêtes et UI.
- Professeur : flags `canCreatePositionAndPreset` et `canDeletePositionAndPreset` ; relation `favoriteDisciplines` (liste d’id de disciplines, cap 5).

## UX & parcours
- Signup : deux champs mot de passe avec oeil, validation “les mots de passe ne correspondent pas”. Message post-création invitant à vérifier l’email.
- Login : si `unverified`, afficher le blocage + CTA “Renvoyer l’email de vérification” (respecter rate-limit). Si désactivé : message “Compte désactivé, contactez l’admin”.
- Admin : switches/boutons dans les vues de gestion (studios, disciplines, utilisateurs) pour désactiver/réactiver ; indication d’état “désactivé” (badge “Désactivé” sur cours existants concernés). Badge/tooltip source côté staff sur cartes liste cours, détail cours, et dans les sélecteurs (studio/discipline) pour signaler l’inactivité. Côté élève : badge générique sur détail cours et listes de ses cours, sans tooltip.
- Super-admin : interface utilisateur avec boutons “Forcer vérif”, “Renvoyer email”, “Désactiver/Réactiver” + log d’audit minimal (action, userId, adminId, horodatage, motif/commentaire optionnel) visible dans l’UI admin. Écran dédié filtrable (action/type/date/user) + tri date desc/pagination simple, page 20 entrées, rétention 90 jours. Actions tracées a minima : disable/enable studio/discipline/user, force-verify-user, resend-verification-email ; log des tentatives refusées (ex : renvoi mail rate-limité, action bloquée par droits) pour support.
- Prof : préférence “disciplines favorites” dans son profil/paramètres ; si droit retiré, masquer les entrées “Créer position/preset” dans la barre/CTA.

## Tests & QA à prévoir
- Signup : prénom/nom obligatoires, double mot de passe, oeil fonctionne, message post-submit affiché.
- Email vérif : mail envoyé à la création ; lien valide 24h ; rate-limit renvoi appliqué ; login bloqué si non vérifié ; forcer vérif (super-admin) débloque le login ; renvoi mail fonctionne.
- Reset password : refus de la demande si compte `unverified` ou désactivé (pas d’email envoyé).
- Archivage : studio/discipline désactivé n’apparaît plus en sélection ni dans les listes utilisateur ; réactivation ré-affiche ; cours existants affichent badge “Désactivé” (élève/prof) mais restent visibles/ouverts pour les inscrits ; aucune nouvelle inscription possible ; données historiques intactes.
- Message non-inscrit : tentative d’inscription sur cours lié à entité désactivée → refus avec message “Inscriptions closes”.
- Désactivation utilisateur : login refusé ; non assignable ; réactivation rend l’accès ; cours futur avec prof désactivé affiche un badge “Désactivé” (pas de notif auto).
- Droit prof : par défaut création/suppression position/preset autorisées ; si `create` retiré → blocage UI et serveur (y compris duplication/clonage/import) ; si `delete` retiré → blocage suppression ; édition de contenus existants toujours OK ; rétablir les droits restaure l’accès (y compris via import).
- Disciplines favorites prof : sélection/affichage persistant, cap 5, UX alignée avec coups de cœur positions.

## Seed & fixtures à prévoir
- Utilisateurs : un compte `unverified`, un compte `verified`, un compte désactivé (élève), un prof avec droit création actif, un prof avec droit création retiré, un admin et un super-admin. Inclure au moins un token de vérif actif/expiré si la logique le permet.
- Studios/Disciplines : un studio et une discipline actifs, un studio et une discipline désactivés (`disabledAt/By` renseignés).
- Cours : 
  - 1 cours référencé sur un studio/discipline actifs (contrôle normal).
  - 1 cours référencé sur un studio désactivé (affiche badge “Désactivé”, inscriptions fermées aux nouveaux).
  - 1 cours futur avec prof désactivé et seul prof (affiche badge, pas de notif auto).
- Prof : jeu de données avec `favoriteDisciplines` (3–5 ids) pour démontrer l’affichage, et un prof sans favoris pour le cas vide.
- Données cohérentes pour QA : mots de passe connus, emails distincts et nominatifs (`unverified.qa@...`, `disabled.qa@...`, `prof-create-off@...`), timestamps réalistes (`verifiedAt`, `disabledAt` quelques jours/semaines), `disabledBy`/`forcedVerifiedBy` pointant vers un admin seed, inscriptions cours existantes pour tester la règle “inscrits maintenus, nouvelles inscriptions refusées”.
- Prendre les secrets/env (`DATABASE_URL`, mailer, NEXTAUTH_*) dans `.env`. Reset DB + reseed autorisé pour tester le flux complet (signup/verif/désactivation/seed).
- Prisma : schema mis à jour (verified/disabled user, flags canCreate/canDelete, disabled studios/disciplines, favoriteDisciplines prof, EmailVerificationToken). `prisma db push` à exécuter avec `DATABASE_URL` (non lancé ici).
