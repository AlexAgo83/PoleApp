# 08_DRY_019 — Boutons contact WhatsApp / Instagram (profil + fiche prof)
[Aligné v0.14.x | Compréhension: 100% | Confiance: 95% | Avancement: 100% | Portée: profil + fiche prof → phone/instagram + CTA externes]

## Objectif
Répondre au QA S018 (2026-01-06, v0.14.x) : permettre aux utilisateurs de renseigner un téléphone (WhatsApp) et un username Instagram, et afficher des boutons d’accès direct sur `/teachers/[id]` et `/profile` quand ces données sont présentes.

## Périmètre (in/out)
- (in) Champs optionnels `phone` et `instagramUsername` stockés côté utilisateur ; édition depuis `/profile`.
- (in) Affichage de deux boutons (WhatsApp / Instagram) sur la fiche prof et la page profil ; ouverture des liens externes si données disponibles.
- (out) Liaison OAuth ou récupération de contenu Instagram/WhatsApp ; messagerie in-app ; gestion des numéros multi-appareils.

## Règles fonctionnelles
- Champs optionnels :
  - `phone` : saisie libre avec espaces/`+`/`-`/parenthèses tolérés ; persistance en numéro normalisé (`+` en tête accepté), longueur 8–20 après nettoyage, vide = suppression.
  - `instagramUsername` : 2–30 caractères, lettres/chiffres/`._` sans espaces ; vide = suppression.
- Boutons :
  - WhatsApp affiché uniquement si `phone` présent ; ouvre `https://wa.me/<phone_normalisé>` dans un nouvel onglet (`rel="noreferrer noopener"`).
  - Instagram affiché uniquement si `instagramUsername` présent ; ouvre `https://www.instagram.com/<username>/` dans un nouvel onglet.
  - Pas d’état désactivé : si aucune donnée, aucun bouton n’apparaît.
- Messages d’erreur attendus (front/back) :
  - Téléphone : “Numéro WhatsApp invalide (8–20 chiffres, + optionnel)” si échec validation/normalisation.
  - Instagram : “Username Instagram invalide (lettres/chiffres/._, 2–30 caractères)” si regex KO.
- Pages :
  - `/teachers/[id]` : boutons alignés à gauche de “Partager”, données du prof affiché ; visibilité contrôlée par les champs du prof.
  - `/profile` : mêmes boutons dans l’entête du premier panel pour l’utilisateur courant.
  - `/teacher/students/[id]` (vue prof sur un élève) : mêmes boutons alignés avec les actions existantes (à gauche de “Partager” ou bloc d’actions), visibles seulement si l’élève a renseigné phone/IG.
- Validation immédiate sur `/profile` (messages clairs) ; règles serveur identiques (normalisation + blocage format invalide).
- RBAC / scope : accès fiche prof déjà restreint aux utilisateurs connectés filtrés par schoolId ; pas de fuite inter-écoles.

## UX cible
- Deux boutons stylisés (icônes WhatsApp/Instagram) sur la même ligne que “Partager” ; hover/focus cohérent (halo/bordure cyan existant).
- Pas d’emplacement vide si données absentes.
- Formulaire profil : labels “Téléphone (WhatsApp)” et “Instagram (username)”, aide courte sur le format, message d’erreur si invalide.
- Accessibilité : `aria-label` explicites, ordre de tab cohérent avec le bouton “Partager”, focus visible.
- Design boutons : réutiliser le même variant que “Partager” (outline/bordure cyan, taille/padding/typo identiques), icône à gauche (monochrome, taille égale à l’icône partage), pas de gradient Instagram (rester dans la charte). Placer WhatsApp puis Instagram à gauche de “Partager” dans la même flex-row/gap ; si pas de données, ne rien rendre. Mobile : autoriser le wrap avec le même `gap` pour conserver la clicabilité. Pour WhatsApp, optionnellement utiliser le bouton officiel vert (SVG/PNG) recommandé par WhatsApp (cf. https://faq.whatsapp.com/5913398998672934/?locale=fr_FR), ex :
  - `<a aria-label="Chat on WhatsApp" href="https://wa.me/1XXXXXXXXXX"><img alt="Chat on WhatsApp" src="WhatsAppButtonGreenLarge.svg" /></a>` ou variante PNG.

## Données / technique
- Modèle `User` : nouveaux champs nullable `phone`, `instagramUsername`.
- Normalisation téléphone côté serveur : retirer espaces/`-`/parenthèses, conserver éventuel `+` initial, rejeter si longueur nettoyée hors 8–20.
- Validation Instagram : regex `^[A-Za-z0-9._]{2,30}$`.
- Actions serveur profil (et éventuelles actions d’édition prof) acceptent/valident/persistent ces champs ; champ vide → `null`.
- Lecture fiche prof / profil : sélectionner systématiquement `phone` et `instagramUsername` dans les requêtes Prisma/actions pour contrôler l’affichage.
- Lecture côté prof pour un élève (`/teacher/students/[id]`) : inclure `phone`/`instagramUsername` dans la requête/loader pour afficher les boutons.
- Boutons = liens externes simples ; pas de SDK ; `target="_blank"` + `rel="noreferrer noopener"`.
- Prévoir migration `prisma migrate`/`db push` pour appliquer les nouveaux champs.
- Seed QA : prévoir au moins un utilisateur/prof avec phone+IG pour vérifier l’affichage, et un sans données pour le cas vide.

## Tests & QA à prévoir
- Profil : saisie valide téléphone + IG → boutons visibles après sauvegarde, liens corrects ; formats invalides → message d’erreur, pas de sauvegarde ; vidage d’un champ → bouton disparaît.
- Profil : champ vidé → valeur `null` en base ; pas de bouton après reload.
- Fiche prof : prof avec téléphone+IG → deux boutons visibles à gauche de “Partager” ; prof sans données → pas de changement de layout.
- RBAC : un utilisateur d’une autre école ne peut pas accéder à une fiche prof interdite (comportement existant inchangé).
- Accessibilité : boutons tab-focusables, `aria-label` explicites.
> Implémenté côté code (actions, UI, normalisation). Tests automatiques non lancés.
> DB reset + seed exécutés (prisma db push --force-reset + db:seed) avec les nouveaux champs.

## Risques / points ouverts
- Formats téléphoniques internationaux : la fenêtre 8–20 peut être trop restrictive pour certains pays.
- Données publiques : afficher un téléphone en clair peut poser une question de consentement ; à confirmer si une bascule de visibilité est nécessaire (non demandée ici).
- Icônes / style : vérifier disponibilité des pictos et cohérence mobile.
