# 08_DRY_014 — Accès positions via achat de preset ou cours (non-premium)
[Aligné v0.13.0 | Confiance: 86% | Avancement: 50% | Portée: RBAC positions/presets/cours]

Objectif : permettre à un utilisateur non-premium qui a acheté un preset ou s’est inscrit à un cours d’accéder aux positions incluses (contenu détaillé, médias, tips), sans lever la restriction premium ailleurs.

## Hypothèses / règles d’accès
- Accès position autorisé si : utilisateur premium OU rôle prof/admin OU position libre (free) OU position présente dans un preset acheté (statut PAID) OU position liée à un cours réservé/payé (inscription élève confirmée) même sans premium.
- Ne pas ouvrir l’accès à toutes les positions : uniquement celles référencées dans les presets/cours pour lesquels l’utilisateur est inscrit/payant (cross-school autorisé pour l’instant).
- Les badges évoluent : afficher un badge “Débloqué par achat” (au lieu de verrou premium) quand l’accès vient d’un achat.

## Étapes proposées
1) Données (source presets) : récupérer les presets achetés `Purchase` kind PRESET, status PAID (exclure pending/refunded). Joindre `preset.positions` pour obtenir les `positionId`.  
   - Option simple : requête qui sort directement les `positionId` des presets payés par l’utilisateur courant.  
   - Pack/abo non concernés ici (ils ne donnent pas de positions).  
2) Données (source cours) : récupérer les cours où l’utilisateur est inscrit via `CourseAttendance` status CONFIRMED (WAITLIST exclu). Joindre `course.positions` pour obtenir les `positionId`.  
   - Pas de `Purchase` kind COURSE dans le schéma : l’inscription confirmée vaut “achat”.  
3) Agrégation : fusionner les deux sources dans un `Set<string>` `purchasedViaPresetOrCourse`. Cross-school autorisé (ne pas filtrer par schoolId tant qu’on n’a pas de notion multi-école stricte).  
4) Loader `/positions/[id]` : injecter `isUnlockedByPurchase = purchasedSet.has(position.id)`. Réécrire `canViewContent = !isStudent || isPremium || isUnlockedByPurchase || hasUnlockedProgress`.  
   - Ajuster les badges : si `isUnlockedByPurchase` est vrai et non-premium, afficher “Débloqué par achat” au lieu du cadenas premium.  
   - Si non débloqué : conserver le placeholder/verrou (pas de tips/médias) ; les vidéos restent signées via `generateSignedUrl` mais l’affichage est conditionné par `canViewContent` étendu.  
5) Pages concernées (vues identifiées) :  
   - `/positions` (liste SSR) : exposer le set `purchasedViaPresetOrCourse` et afficher le badge “Débloqué par achat” sur les cartes concernées.  
   - `/positions/[id]` : gating médias/texte via `canViewContent` incluant `isUnlockedByPurchase`, badge “Débloqué par achat” (discret, en bas du panneau infos), placeholder/verrou si non débloqué.  
   - `/student/progress` : liste de positions (SafeImage, pas de gating médias aujourd’hui) → afficher le badge si débloqué, possibilité d’utiliser le set pour cacher les tips si on gate plus tard.  
   - Autres vues positions (cours/presets affichent déjà des positions mais achat implicite) : pas de gating supplémentaire identifié, à confirmer si un widget positions nécessite le set.
6) Perf : volumétrie attendue 300–500 positions, 50–100 combos, potentiellement >100 positions débloquées par utilisateur : un `Set` d’ids reste léger. Implémentation SSR : une requête par source (presets payés / cours confirmés) puis fusion en mémoire. Si besoin, filtrer les requêtes par `positionId in (...)` sur les vues critiques pour éviter de charger tout.  
7) Tests (à écrire) :  
   - non-premium sans achat : contenu premium bloqué (badge verrou, pas de tips/médias).  
   - non-premium avec preset contenant la position : contenu visible + badge “Débloqué par achat”.  
   - non-premium inscrit à un cours contenant la position (CourseAttendance CONFIRMED) : contenu visible + badge “Débloqué par achat”.  
   - premium : contenu visible (badge premium standard).  
   - prof/admin : contenu visible.  
   - (optionnel) suppression preset/cours : recalcul du set → accès révoqué.  
   - (optionnel) cross-school : accès maintenu si débloqué via achat d’une autre école.

## Risques / points à confirmer
- Volume de positions débloquées : préférer un `Set` d’ids calculé via requêtes ciblées (IN) plutôt que de charger tout si la volumétrie devient importante.
- Vérifier les endroits où `canViewPremium` est dérivé pour ne pas casser d’autres règles (par ex. gating des médias Cloudinary).
- Cross-school accepté pour l’instant ; à restreindre le jour où on introduit un scoping école sur presets/cours.
- Gating actuel : dans `/positions/[id]`, les vidéos sont toujours signées mais l’accès est géré par `canViewContent = !isStudent || isPremium || hasUnlocked`. Il faut remplacer/étendre `hasUnlocked` par le set `purchasedViaPresetOrCourse` et ajuster le badge “Débloqué par achat”.
- Inscription cours : pas de `Purchase` kind COURSE ; l’inscription est `CourseAttendance` (status CONFIRMED). Brancher le déblocage dessus, pas sur `Purchase`.
- Perf attendue : avec ~300–500 positions et 50–100 combos, un `Set` d’ids en mémoire reste léger ; on peut néanmoins filtrer les requêtes par `positionId in (...)` sur les vues critiques si besoin.
- Cours : inclure toutes les attendances CONFIRMED (cours passés compris) pour déverrouiller les positions.
- Cross-school : accès conservé même si l’achat a été fait dans une autre école (scoping à voir plus tard).
- Révocation : si un preset/cours est supprimé, l’accès se révoque naturellement (set recalculé à chaque chargement).
- Construction serveur :  
  - Requêtes Prisma minimales par utilisateur :  
    * `purchase.findMany({ where: { userId, kind: "PRESET", status: "PAID" }, select: { offerId: true } })` + `presetPosition.findMany({ where: { presetId: { in: presetIds } } })`  
    * `courseAttendance.findMany({ where: { studentId: userId, status: "CONFIRMED" }, select: { course: { select: { positions: { select: { positionId: true } } } } } })`  
  - Fusion côté loader en `Set<string>` sans exposer d’autres infos (pas de leak d’ids de cours/presets).  
  - Injection dans les loaders `/positions`, `/positions/[id]`, `/student/progress` via props/params SSR ; pas de requêtes supplémentaires sur le client.
